## 一、你提出的三个问题，我的评估

### 1. “数据库的数据是固定写入的”—— 对，这是演示数据设计问题

现状：`DBManager_seed.cpp` 用 C++ 常量数组 + 固定公式生成数据，数据“焊死”在代码里。

问题：
- **改演示数据要重新编译**，前端/老师想换一组数据没法直接改；
- 生成逻辑太规则：近 3 天每天每站固定 2 单、每站 6 台桩的固定排布、无周末效应、
  无时段分布——图表、机器学习训练起来“一看就是假的”；
- 种子的时间范围只有 3 天，但 UC-D-02 要求“约 30 天的历史订单”（给营收图表和 ML 训练）。

改进方向（三选一或组合）：
| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| A. 数据文件化 | 把站点/用户等“静态数据”放 `seed/*.json`（或 .csv），程序启动读取导入 | 改数据不用编译 | 多一套文件读取逻辑 |
| B. 可复现生成器 | 保留代码生成，但用**固定随机种子** + 真实分布（周末单量高、晚高峰、快慢充时长不同）生成 30 天数据 | 数据更像真实、可复现、改动只在一处 | 仍需重新编译才换数据 |
| C. 管理端造数据（结合） | 种子只放最小集，日常演示数据由管理端接口（新增电站/建桩/调价，已实现）与“模拟充电脚本”生成 | 最能体现系统能力 | 需要写模拟脚本 |

建议：**B 为主 + 数据范围扩到 30 天**（单量、时长、价格都要带分布），A 看你时间，C 属于锦上添花。

### 2. “test.h 应该消除”—— 同意，但要先想清楚“测试放哪”

`test.h` 目前是“控制台演示函数集”，它是**开发期验证工具**，不是产品功能，不应出现在最终交付里。
但直接删掉会导致没人回归验证，所以关键是先给它找到新家：

| 去处 | 做法 | 适合 |
| --- | --- | --- |
| Qt Test 单测 | 建 `tests/tst_dbmanager.cpp`（`QT += testlib`），把 DB 方法断言写成 `QVERIFY` | 想认真回归 DB 层 |
| 独立 demo 程序 | 拆成 `demo.cpp` 单独一个可执行文件，不编进主程序 | 想保留演示又不污染主入口 |
| 外部脚本 | 把 `build/v3/rest_test.py` 这类 HTTP 冒烟测试收进 `scripts/`，算“接口测试” | 配合 REST 版最好用 |

建议：DB 层关键路径（orderConnect→orderStart→orderFinish 状态机）值得留一组自动化断言；
至少要做到**主程序入口里不再 include test.h**，交付构建不含演示逻辑。
另外验收需要的“截图数据”可以靠生成器（见 1-B）临时灌出，不靠 test.h。

### 3. “SQL 弄到专门 .sql 文件里”—— 部分同意，分两层看

先分清两种 SQL：
- **DDL/迁移类**（建表、加字段、建索引）：**非常建议**抽成 `.sql` 文件；
- **业务查询类**（每个方法里的 INSERT/SELECT）：**不建议**为抽而抽，理由见下。

#### 3a. DDL / 迁移脚本文件化（推荐做）

这正是你在《学习到的.md》里记的“增量脚本”的完整形态：

```
db/
  schema.sql            # 当前最新结构的完整建表脚本（文档/对照用）
  migrations/
    001_station_code_prefix.sql
    002_charger_status_remap.sql
    003_xxx.sql         # 以后每次改动加一个
```

配合已做好的 `schema_version` 机制，让 `applyMigrations()` 改为：
启动读版本 → 按文件名顺序执行 `db/migrations/*.sql` 里尚未执行的脚本（每个事务）→ 更新版本号。

实现要点（Qt 下三种读法）：
| 读法 | 说明 | 评价 |
| --- | --- | --- |
| QRC 资源嵌入（`db.sql` 文件 + `:/db/migrations/...`） | 编译进程序，部署无路径问题 | 推荐，最稳 |
| 程序目录下外部文件 | 可以直接改 sql，但部署要带文件、路径要处理 | 灵活但麻烦 |
| 生成时读、别时无 | 不稳定 | 不推荐 |

> 注：纯 SQL 无法表达“查表结构看列是否存在再 ALTER”这类守卫，迁移里偶尔保留少量
> C++ 判断是可以的（文件只写“纯 SQL 能表达的那部分”）。

#### 3b. 业务 SQL 集中与否（不做也不扣分）

- 现状业务 SQL 都内联在各自的 `DBManager_*.cpp` 方法里，**全部使用参数化绑定**、就近可读。
- 需求说明书 NFR-M-02 只要求“UI 层不出现 SQL；SQL 只存在于 database/service 层”，当前实现**已经满足**。
- 硬抽到一个大 `sql.h`/`.sql` 常量文件反而会拆散“方法 = 一段 SQL + 结果映射”的可读性。
- 如果你想给 SQL 做“统一管理”，更好的中间态是：为每张表封装清楚的 DAO 方法（现在已接近），
  命名统一、禁止字符串拼接——这比文件化更重要。

### 安全和稳健性

| 项目 | 现状 | 建议 |
| --- | --- | --- |
| 管理员密码明文 | 明文存 admin 表 | NFR-S-01 要求 SHA-256 加盐；建议做（迁移时把种子密码改哈希+登录方法改哈希校验） |

| 日志 | 全是 qDebug 控制台 | 验收要截图时可临时重定向；正式版加 QLoggingCategory + 文件日志（NFR-M-04） |

## 四、一句话总结

你现在的三个想法里：
- **“数据固定写入”** → 值得改（30 天+随机分布或数据文件化）；
- **“消除 test.h”** → 同意，但要先给它找好新家（单测/独立 demo/脚本），别裸删；
- **“SQL 归到 .sql”** → 分两层：**建表/迁移脚本**建议抽文件；**业务 SQL** 保持内联参数化即可（当前已合规）。
再加最容易被验收一眼看出的两件事：**BR-02/03 的数据库级约束**和**三张缺失表的补齐**。
